# GitHub playbook

How this repository runs like a team project. The rules are in
[project-workflow.md](./agents/project-workflow.md). This file is the click-by-click
version for this repository.

## Who does what

| Role | Who | Does |
| --- | --- | --- |
| Lead and reviewer | **Alex** | Writes or approves issues, reviews every pull request, merges, publishes releases |
| Developer | **Claude** (agent) | Drafts issues, works on a branch, opens pull requests, answers review comments |
| Maintenance bot | **Dependabot** | Opens dependency update pull requests |
| Gatekeeper | **CI** (GitHub Actions) | Runs typecheck, lint and build on every pull request |

Work in this order: **Part A** once, **Part B** once, then **Part C** for every issue.
**Part D** is a warm-up review on real Dependabot pull requests.

2. **Choose a tag** → type `v1.0` → **Create new tag: v1.0 on publish**.
   **Target:** `main`.
3. **Release title:** `v1.0 · Initial public release`.
4. **Describe this release:** paste the `v1.0` section of `CHANGELOG.md`, from `### Added`

## Part C: the team loop for every issue

### C1. Create the issue (you, about 5 minutes)

1. **Issues → New issue → Feature** (or **Fix** / **Task**).
2. **Title:** the spec's title, for example
   `feat(cms): connect Storyblok`.
3. Paste the spec's **Context**, **Goal**, **Acceptance criteria** and **Constraints** from
   [issue-drafts.md](./issue-drafts.md) into the matching fields.
4. Right sidebar:
   - **Labels:** `feature`, `fix`, `docs`, `refactor` or `chore`
   - **Milestone:** `v2.0 — Full stack`
   - **Projects:** `Ethan Olson portfolio` (Status: **Todo**)
   - **Relationships → Mark as blocked by:** the issues it depends on, if any
5. **Create.** Note its number (for example `#12`) and update the "S" references in
   later specs.

### C2. Hand it to the agent

- With the GitHub App: comment on the issue
  `@claude please implement this issue, following CLAUDE.md.`
- With Claude Code locally: in the terminal, say `Work on issue #12.`

Move the card to **In Progress**.

### C3. The agent works (you wait for the notification)

The agent creates `feat/12-connect-storyblok` from the latest `main`, makes small
Conventional Commits, runs the checks, and opens a pull request with the template filled
in and `Closes #12` at the bottom. CI starts automatically. Move the card to **In review**.

### C4. Review the pull request (you, the important part)

1. **Conversation tab:** read *What*, *Why* and *How to test*. Is every acceptance
   criterion from the issue covered?
2. **Checks tab:** CI must be green. If it's red, open **Details** to see why.
3. **Files changed tab**, file by file:
   - Click **+** next to a line to comment on it, then **Start a review** (comments are
     batched and sent together).
   - To propose a concrete fix, click the ± icon in the comment box. It inserts a
     ` ```suggestion ` block the agent can apply with one click.
   - Tick **Viewed** on each file you've finished.
4. **Try it locally** when it's visible on the page:
   `git fetch origin && git switch feat/12-connect-storyblok && npm install && npm run dev`.
5. **Review changes** (top right of Files changed), and pick one:
   - **Request changes:** something misses the acceptance criteria or is wrong.
   - **Comment:** questions only.
   - **Approve:** everything meets the issue.

### C5. The agent answers the review

It replies to each comment and pushes **new commits to the same branch**, never a new pull
request. With the app, write `@claude please address the review comments.` Then:

- Check the new commits (**Files changed → Changes from: last review**).
- **Resolve conversation** on each comment that's addressed.
- **Approve** when it's done. Back to C4 otherwise.

### C6. Merge (you)

1. All green: CI passed, approved, every conversation resolved.
2. **Squash and merge**. Edit the title to a Conventional Commit:
   `feat(cms): connect Storyblok (#12)`. **Confirm squash and merge.**
3. Automatically: the branch is deleted, the issue closes (`Closes #12`), and the card
   moves to **Done**.
4. Locally: `git switch main && git pull`.

### C7. When the milestone is done

1. An issue and a pull request that add a `v2.0` section to `CHANGELOG.md` (Added / Changed
   / Fixed).
2. Merge it, then publish `v2.0` exactly like Part B, with title
   `v2.0 · Full stack`.
3. **Issues → Milestones → `v2.0 — Full stack` → Close.**

## Part D: warm-up review with Dependabot

Once Dependabot has reopened its pull requests (A7, step 2), practise C4–C6 on them. Its
pull request description includes release notes and a changelog.

- **Minor and patch group** (`chore(deps): bump the minor-and-patch group…`): if CI is
  green and the notes show nothing alarming, **Approve → Squash and merge**.
- **GitHub Actions bumps** (`actions/checkout`, `actions/setup-node`): read the release
  notes for breaking changes, then approve and merge if CI passes.
- **Major versions** (for example TypeScript 7, ESLint 10): these deserve their own issue.
  Comment `@dependabot ignore this major version` to close the pull request and stop that
  major for now, or `@dependabot close` to just close it.
- Other useful commands: `@dependabot rebase` (update the branch), `@dependabot recreate`.

`@types/node` majors are already ignored in `.github/dependabot.yml`, because the types
should match the Node.js version that runs the site (24).
